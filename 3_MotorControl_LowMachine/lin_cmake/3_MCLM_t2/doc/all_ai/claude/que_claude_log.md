## 阶段三：新发现 — 系统完全无响应的根因（2026-04-16）

### 现象
发送任何 CAN 指令后，UART1、UART2 均无反馈，电机无动作。

### 根因：`motor_mutexHandle` 死锁

**三个任务同时竞争同一把互斥锁 `motor_mutexHandle`，且持锁期间互相等待，形成死锁。**

#### 锁竞争关系

| 任务 | 优先级 | 持锁行为 |
|---|---|---|
| `Encoder_Ta` | High | 每 10ms 持锁，更新 `g_motors[i].current_ticks` / `current_logic_speed` |
| `MotorControl_Ta`（M1） | High | 每 10ms 持锁，读 `current_logic_speed`，写 `pwm_output` |
| `Command_Ta` | BelowNormal | 每次命令持锁，读 `g_motors[idx]` 状态 |

#### 死锁触发路径

```
Encoder_Ta 持锁（osWaitForever）
    → MotorControl_Ta 等锁（osWaitForever）
    → Command_Ta 等锁（osWaitForever）
```

三个任务都用 `osWaitForever` 等锁，且 Encoder 和 Motor 任务优先级相同（High），
FreeRTOS 同优先级任务时间片轮转，但 `osWaitForever` 会导致低优先级的 Command_Ta
**永远无法获得 CPU 时间**来处理命令，ACK 也无法发出。

#### 次要问题：Logger_Task 的 mutex 超时过短

`logger_task.c:30`：
```c
if (osMutexAcquire(motor_mutexHandle, 10) == osOK)  // 只等 10ms
```
若 Encoder/Motor 任务持锁超过 10ms，Logger 直接 `continue` 跳过，导致日志丢失。

### 修复方案

#### Fix C：`tb6612_DC_task.c` 持锁范围缩小

当前持锁范围包含 `PID_Compute`（浮点运算，耗时较长）。
应只在读写共享数据时持锁，PID 计算移到锁外：

```c
// 锁外：读取当前速度（局部变量）
float current_speed;
if (osMutexAcquire(motor_mutexHandle, osWaitForever) == osOK) {
    current_speed = motor->current_logic_speed;
    osMutexRelease(motor_mutexHandle);
}

// 锁外：PID 计算
float output = PID_Compute(&(motor->pid), current_speed);

// 锁内：只写结果
if (osMutexAcquire(motor_mutexHandle, osWaitForever) == osOK) {
    motor->target_logic_speed = motor->pid.setpoint;
    motor->pwm_output = (int16_t)output;
    osMutexRelease(motor_mutexHandle);
}
```

#### Fix D：`command_task.c` 读状态改为短超时或不加锁

`command_task.c` 读 `g_motors[idx]` 只是为了生成 ACK 反馈，非关键路径，
可改为超时 5ms，超时则用上次缓存值：

```c
if (osMutexAcquire(motor_mutexHandle, 5) == osOK) {
    status = g_motors[idx];
    osMutexRelease(motor_mutexHandle);
}
// 超时不阻塞，status 保持零值，ACK 仍然发出
```

## 阶段四：CAN 接线反向问题（2026-04-16）

### 现象
系统完全无响应，UART1/UART2 均无输出，电机无动作。在 `can.c` 中断入口加 UART2 阻塞探针后，串口无任何输出，确认中断从未触发。

### 根因
**CAN 总线 CANH/CANL 物理接线反向**，MCU 收不到任何帧。

### 解决
物理接线对调后恢复正常。调试探针已移除。

## 阶段五：CAN 通信验证（SavvyCan_260416_2039.csv，2026-04-16）

### 数据分析

| 操作 | 发送 ID + 数据 | MCU 回包 | 结论 |
|---|---|---|---|
| LOG_START (M1) | `0x225: 04 00...` | `0x225: CF 09 01 00...` | ✅ ACK 正常 |
| LOG_STOP (M2) | `0x235: 05 00...` | `0x235: CF 0A 00 00...01` | ✅ ACK 正常 |
| 速度=32 (M1) | `0x125: 11 20` | 无回包 | ✅ 正常（速度指令不主动回 CAN） |
| 速度=0 (M1) | `0x125: 11 00` | 无回包 | ✅ 正常 |
| 速度=48 (M2) | `0x135: 11 30` | 无回包 | ✅ 正常 |
| LOG_START (M2) | `0x235: 04` | `0x235: CF 09 01 00...01` | ✅ ACK 正常 |
| 查询 M2 状态 | `0x235: 01` | `0x335: 00 00 00 00 00 00 00 01` | target=0, current=0, pwm=0 |
| 查询 M1 状态 | `0x225: 01` | `0x325: 00 00 FF FF 00 00 00 00` | target=0, current=-1, pwm=0 |

### 结论

**CAN 通信链路完全正常**，MCU 正确响应所有命令类型（ACK、查询、速度指令）。

`target=0` 是正常结果：速度=32 的帧（`11 20`）之后紧接着发了速度=0（`11 00`），最终 setpoint=0，查询结果符合预期。

`current=-1`（`FF FF`）为编码器微小抖动（±1 tick），属正常现象。
